# AI Production of Oil — мониторинг добычи near-real-time

## О проекте

Внутренняя система near-real-time мониторинга добычи нефти и газа для
нефтегазовой компании в Казахстане. Это **слой аналитики над SCADA**,
не замена SCADA и не система управления.

Система решает 5 задач:

1. **Сбор данных** о добыче из разнородных источников в единую БД
2. **Автоматическая валидация** замеров дебитов (сейчас это делается
   глазами в Excel)
3. **Аллокация** суточной добычи по скважинам (back-allocation)
4. **Расчёт потерь добычи** (deferred production) с разложением по причинам
5. **Алерты об аномалиях** + сопоставление факта с прогнозом
   гидродинамической модели

## Ключевые ограничения

- Система **только читает** данные. Никогда ничего не пишет в контур АСУ ТП.
- Развёртывание **on-premise**, внутри корпоративного контура. Никакого облака.
- Реальных данных пока нет (идёт согласование доступа). Разработка ведётся
  на **синтетических данных**, которые генерируются сами. Архитектура
  должна позволять подменить источник данных без переписывания логики
  расчётов (источник данных изолирован в `src/ingestion/`, остальной код
  работает с доменными моделями, а не с форматом конкретного источника).
- Автор проекта — не профессиональный разработчик. Код должен быть
  читаемым, с комментариями на русском в местах, где есть промысловая логика.

## Стек

- **Python 3.11+** — основной язык
- **PostgreSQL 16 + TimescaleDB** — хранение таймсерийных данных о добыче
- **SQLAlchemy 2.0 + Alembic** — ORM и миграции схемы БД
- **FastAPI** — REST API
- **pandas, numpy, scipy** — расчёты (аллокация, DCA, валидация)
- **pytest** — тесты
- **Docker Compose** — локальный запуск БД для разработки
- Позже: **Prefect** (оркестрация пайплайнов), **Telegram-бот** (алерты),
  **React+ECharts или Power BI** (UI)

Стек утверждён, альтернативы не предлагать без веской причины.

## Структура репозитория

```
src/
  ingestion/    — сбор и нормализация данных из источников (SCADA-выгрузки,
                  ручной ввод, синтетический генератор). Единственное место,
                  которое знает о формате конкретного источника.
  domain/       — доменные модели и бизнес-сущности (скважина, ГУ, замер и т.д.)
  calc/         — расчётные модули: валидация замеров, аллокация,
                  deferred production, DCA
  api/          — FastAPI-приложение, роуты
  alerts/       — логика алертов об аномалиях
migrations/     — миграции схемы БД (Alembic)
tests/          — тесты (pytest), структура зеркалит src/
scripts/        — вспомогательные утилиты, генератор синтетических данных
docs/           — документация, схемы БД, диаграммы
docker/         — Docker-related файлы (Dockerfile, init-скрипты для БД)
```

## Соглашения

- **Нейминг**: код (переменные, функции, классы) — на английском, по
  стандартным Python-конвенциям (snake_case для функций/переменных,
  PascalCase для классов). Комментарии, объясняющие промысловую логику —
  на русском. Доменные термины (UWI, ГФ, КЭ и т.д.) в коде — латиницей
  транслитерацией или английским эквивалентом (см. глоссарий ниже), но в
  комментариях и docstring можно писать как есть по-русски.
- **Язык комментариев**: русский — там, где логика завязана на промысловую
  специфику (формулы, единицы измерения, допущения). Обычные технические
  комментарии (почему так реализовано на уровне кода) — на усмотрение,
  предпочтительно тоже по-русски для единообразия.
- **Обработка ошибок**: не глотать исключения молча. На границах системы
  (приём данных из источника, API-запросы) — валидировать и явно сообщать
  об ошибке. Внутри домена — доверять инвариантам, не городить defensive
  try/except на случаи, которые не могут произойти.
- **Тесты**: каждый расчётный модуль (`src/calc/*`) обязательно
  сопровождается тестами с понятными числовыми примерами (не просто
  моками — реальные числа, которые можно проверить в столбик/Excel).

## Глоссарий предметной области

| Термин | Значение |
|---|---|
| **UWI** | Уникальный идентификатор скважины, сквозной ключ по всей системе |
| **Qж / Qн / Qв / Qг** | Дебит жидкости / нефти / воды / газа |
| **Обводнённость (water cut)** | Доля воды в продукции, % |
| **ГФ** | Газовый фактор, м³/т |
| **Рзаб / Рбуф / Ртруб / Рзатр** | Давление забойное / буферное / трубное / затрубное |
| **АГЗУ** | Автоматизированная групповая замерная установка |
| **ГУ / ДНС** | Групповая установка / дожимная насосная станция |
| **КЭ** | Коэффициент эксплуатации (доля времени работы скважины за период) |
| **ЭЦН / ШГН** | Электроцентробежный насос / штанговый глубинный насос |
| **МРП** | Межремонтный период |
| **ГТМ** | Геолого-техническое мероприятие |
| **ТРС / КРС** | Текущий / капитальный ремонт скважины |
| **Аллокация (back-allocation)** | Распределение замеренной на ГУ добычи по скважинам |
| **Deferred production** | Потери добычи = (потенциал − факт) × время |
| **DCA** | Decline curve analysis, анализ кривых падения (метод Арпса) |
| **History matching** | Адаптация гидродинамической модели на историю разработки |

## Не делать

Сознательно **не реализуем** в рамках этой системы:

- **Запись/управление в контур АСУ ТП.** Система строго read-only
  по отношению к промысловым объектам.
- **Замену SCADA** или дублирование её функций реального времени.
  Это аналитический слой поверх, не диспетчерская система.
- **Облачное развёртывание.** Только on-premise, внутри корпоративного контура.
- **Универсальный коннектор "под любой источник данных".** Строим под
  конкретные источники, которые реально появятся, без абстракций "на будущее".
- **Автоматическое принятие решений/управляющих воздействий** на основе
  алертов — система только информирует, решения принимает инженер.
- **Замену гидродинамической модели** расчётами внутри системы. Прогноз
  модели — внешний вход, который сравнивается с фактом, не пересчитывается.

## Правила работы с автором проекта

- Прежде чем писать код по новой задаче — **сначала предложить план и
  дождаться "ок"**.
- Если промысловая логика неясна — **спрашивать, не придумывать формулу
  самостоятельно**.
- **Никакого over-engineering**: не добавлять абстракции "на будущее".
- Каждый расчётный модуль сопровождается **тестами с понятными числовыми
  примерами**.
- Писать **небольшими итерациями**, после каждой — запускать тесты.
