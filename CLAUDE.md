# AI Production of Oil — мониторинг добычи near-real-time

## О проекте

Внутренняя система near-real-time мониторинга добычи нефти и газа для
нефтегазовой компании в Казахстане. Это **слой аналитики над SCADA**,
не замена SCADA и не система управления.

Система решает 5 задач:

1. **Сбор данных** о добыче из разнородных источников в единую БД
2. **Автоматическая валидация** замеров дебитов (сейчас это делается
   глазами в Excel)
3. **Аллокация** суточной добычи по скважинам (back-allocation)
4. **Расчёт потерь добычи** (deferred production) с разложением по причинам
5. **Алерты об аномалиях** + сопоставление факта с прогнозом
   гидродинамической модели

## Ключевые ограничения

- Система **только читает** данные. Никогда ничего не пишет в контур АСУ ТП.
- Развёртывание **on-premise**, внутри корпоративного контура. Никакого облака.
- Реальных данных пока нет (идёт согласование доступа). Разработка ведётся
  на **синтетических данных**, которые генерируются сами. Архитектура
  должна позволять подменить источник данных без переписывания логики
  расчётов (источник данных изолирован в `src/ingestion/`, остальной код
  работает с доменными моделями, а не с форматом конкретного источника).
- Автор проекта — не профессиональный разработчик. Код должен быть
  читаемым, с комментариями на русском в местах, где есть промысловая логика.

## Соглашения

- **Нейминг**: код (переменные, функции, классы) — на английском, по
  стандартным Python-конвенциям (snake_case для функций/переменных,
  PascalCase для классов). Комментарии, объясняющие промысловую логику —
  на русском. Доменные термины (UWI, ГФ, КЭ и т.д.) в коде — латиницей
  транслитерацией или английским эквивалентом (см. глоссарий ниже), но в
  комментариях и docstring можно писать как есть по-русски.
- **Язык комментариев**: русский — там, где логика завязана на промысловую
  специфику (формулы, единицы измерения, допущения). Обычные технические
  комментарии (почему так реализовано на уровне кода) — на усмотрение,
  предпочтительно тоже по-русски для единообразия.
- **Обработка ошибок**: не глотать исключения молча. На границах системы
  (приём данных из источника, API-запросы) — валидировать и явно сообщать
  об ошибке. Внутри домена — доверять инвариантам, не городить defensive
  try/except на случаи, которые не могут произойти.
- **Тесты**: каждый расчётный модуль (`src/calc/*`) обязательно
  сопровождается тестами с понятными числовыми примерами (не просто
  моками — реальные числа, которые можно проверить в столбик/Excel).

## Глоссарий предметной области

| Термин | Значение |
|---|---|
| **UWI** | Уникальный идентификатор скважины, сквозной ключ по всей системе |
| **Qж / Qн / Qв / Qг** | Дебит жидкости / нефти / воды / газа |
| **Обводнённость (water cut)** | Доля воды в продукции, % |
| **ГФ** | Газовый фактор, м³/т |
| **Рзаб / Рбуф / Ртруб / Рзатр** | Давление забойное / буферное / трубное / затрубное |
| **АГЗУ** | Автоматизированная групповая замерная установка |
| **ГУ / ДНС** | Групповая установка / дожимная насосная станция |
| **КЭ** | Коэффициент эксплуатации (доля времени работы скважины за период) |
| **ЭЦН / ШГН** | Электроцентробежный насос / штанговый глубинный насос |
| **МРП** | Межремонтный период |
| **ГТМ** | Геолого-техническое мероприятие |
| **ТРС / КРС** | Текущий / капитальный ремонт скважины |
| **Аллокация (back-allocation)** | Распределение замеренной на ГУ добычи по скважинам |
| **Deferred production** | Потери добычи = (потенциал − факт) × время |
| **DCA** | Decline curve analysis, анализ кривых падения (метод Арпса) |
| **History matching** | Адаптация гидродинамической модели на историю разработки |

### 2026-09-16: Схема БД слоя данных

Контекст: нужно спроектировать мастер-данные, справочники и таймсерии
для сбора/валидации/аллокации добычи, с разделением на обычные таблицы
PostgreSQL и TimescaleDB hypertables.

Решение:
- 18 таблиц: 8 мастер-данных (`field`, `reservoir`, `well`, `well_alias`,
  `completion`, `equipment`, `gathering_node`,
  `well_gathering_node_history`), 3 справочника-сида (`downtime_reason`
  — иерархический через `parent_id`, `gtm_type`, `measurement_tag`),
  7 hypertables (`measurement`, `well_test`, `daily_production`,
  `node_production`, `downtime`, `gtm_event`, `lab_analysis`).
- Перечисляемые поля (`well_type`, `status`, `equipment_type` и т.д.) —
  `VARCHAR + CHECK`, а не native Postgres `ENUM`: добавление нового
  значения делается обычной миграцией `ALTER TABLE ADD CONSTRAINT`, без
  блокировок `ALTER TYPE`.
- `well_gathering_node_history` — отдельная таблица истории привязки
  скважины к узлу сбора (`valid_from`/`valid_to`), т.к. скважину могут
  перевести на другой узел, а история переводов нужна для аллокации
  задним числом.
- Партиционный столбец времени у каждой hypertable — часть PK (требование
  TimescaleDB). Чанки: 1 день для `measurement` (плотная телеметрия),
  1 месяц — для остальных таймсерий.
- Сжатие TimescaleDB — только для `measurement` (данные старше 30 дней,
  `compress_segmentby = well_id, tag_id`).
- Три Alembic-миграции: (1) `CREATE EXTENSION timescaledb`,
  (2) создание всех обычных таблиц (автосгенерирована из моделей,
  проверена на локальном PostgreSQL), (3) `create_hypertable` +
  политика сжатия (не проверена в этой среде — TimescaleDB недоступна
  без Docker Hub, см. "Не делать / ограничения окружения" ниже).

Последствия: изменение состава допустимых значений CHECK-полей — это
всегда новая миграция с `ALTER TABLE ... DROP CONSTRAINT` +
`ADD CONSTRAINT`, а не правка enum на уровне БД.

### 2026-09-16: well_test хранит сырые данные — сняты CHECK на правдоподобность

Контекст: при разработке генератора синтетических данных понадобилось
записать заведомо "грязные" замеры (обводнённость 105%, отрицательный
дебит) — это тестовые случаи для будущего модуля валидации (src/calc).
Изначальная схема запрещала такие значения на уровне CHECK
(`water_cut BETWEEN 0 AND 100`, `q_* >= 0`), из-за чего БД отказывала бы
в записи сырых (ещё не провалидированных) замеров.

Решение: сняты CHECK-ограничения на физическую правдоподобность значений
в `well_test` (`ck_well_test_q_liquid_nonneg`, `_q_oil_nonneg`,
`_q_water_nonneg`, `_q_gas_nonneg`, `_water_cut_range`, `_gor_nonneg`) —
миграция `c871f01a546d`. Осталось только структурное ограничение
`ts_end > ts_start`. Обоснование: у `well_test` для того и есть
`is_valid`/`validation_flags`, что это сырые данные ДО валидации;
обнаруживать физически невозможные значения — задача модуля валидации,
а не БД. Остальные таблицы (`daily_production`, `node_production`,
`downtime`) — это уже посчитанные/аллоцированные результаты, там строгие
CHECK остаются к месту.

### 2026-09-16: Генератор синтетического промысла

Контекст: реальных данных пока нет (согласование доступа не завершено),
нужен физически правдоподобный набор данных для разработки валидации,
аллокации и алертов.

Решение:
- `scripts/generate_synthetic_field.py` + пакет `scripts/synthetic/` +
  `scripts/synthetic_config.yaml`. Вся физика/параметры — в конфиге,
  seed фиксирован.
- Дебит нефти — гипербола Арпса `q(t) = qi / (1 + b·Di·t)^(1/b)`,
  `t` считается от начала истории мониторинга (не от даты бурения) —
  так `qo_initial` из конфига напрямую соответствует "дебиту в начале
  наблюдаемого периода", как в постановке задачи.
- Обводнённость и ГФ — логистические S-кривые; переход ГФ на новое
  плато привязан не к реальному расчёту Pпл (у нас нет модели пласта),
  а к случайному "дню прохождения точки насыщения" на скважину —
  упрощение, отмечено в коде (`decline.py`, `simulate.py`).
- ГТМ меняют кривую Арпса через "регимы": скачок `qi` вверх +
  ускорение `Di`, начиная с даты ГТМ.
- **Важная корректировка схемы**: `well_test` хранит СЫРЫЕ замеры до
  валидации, поэтому физические CHECK (water_cut 0-100, q>=0) с него
  сняты — иначе нельзя было бы сохранить намеренно "грязные" примеры
  (обводнённость 105%, отрицательный дебит), которые как раз нужны для
  тестирования будущего модуля валидации. Подробности — в записи выше
  ("well_test хранит сырые данные").
- Запись в БД — bulk executemany пачками по 20k строк через SQLAlchemy
  Core (`scripts/synthetic/writer.py`), не через ORM построчно — на
  полной конфигурации (40 добывающих, 3 года, телеметрия раз в 4 часа)
  это ~1.6 млн строк в `measurement`, вставка занимает ~1 минуту.
- CSV-дубликат пишется в `data/synthetic/`, в git не коммитится (см.
  .gitignore) — на полной конфигурации это ~100 МБ.

Последствия: при изменении набора причин простоя/видов ГТМ в
`scripts/synthetic/catalogs.py` нужно синхронизировать со
справочниками, которые заведёт будущий реальный ingestion.

### 2026-09-16: Слой загрузки (src/ingestion) — пишет в measurement, не в daily_production

Контекст: нужна плагинная архитектура источников данных (CSV/Excel
рапорты, синтетика, будущий OPC UA) с единым внутренним форматом и
идемпотентной загрузкой.

Решение:
- Натуральный ключ upsert `(well_id, ts, tag)` — это PK таблицы
  `measurement`, не `daily_production` (`(well_id, date)`, без tag).
  Поэтому ingestion **всегда** пишет в `measurement` (сырой слой),
  независимо от источника: и суточный CSV-рапорт, и будущая телеметрия
  OPC UA превращаются в записи вида `(скважина, время, тег, значение)`.
  `daily_production` — результат будущей аллокации (src/calc), ingestion
  её не трогает.
- Справочник `measurement_tag` расширен тегами суточного рапорта
  (`q_oil_daily`, `q_liquid_daily`, `q_water_daily`, `q_gas_daily`,
  `hours_on_daily`) — перенесён в `src/domain/catalogs.py` (был только в
  `scripts/synthetic/`), т.к. это теперь core-справочник приложения, а
  не только для синтетики.
- `DataSource` (ABC): `read(period)`, `validate_schema()`,
  `get_metadata()`. Реализации: `CsvSource` (CSV/Excel, гибкий
  YAML-маппинг колонок, многострочные шапки и объединённые ячейки в
  Excel через ручной разворот `openpyxl.merged_cells`), `SyntheticSource`
  (читает CSV генератора как будто это внешний фид — "разрешает"
  well_id/tag_id обратно в внешние коды через well_alias/measurement_tag,
  чтобы пройти тот же путь резолюции, что и настоящий источник),
  `OpcUaSource` (только структура, TODO).
- Источник никогда не пропускает нечитаемую строку молча — либо
  `RawRecord` с `parse_error`, либо (для целого файла) `SourceValidationError`.
  Обе ветки уходят в `ingestion_quarantine`/`ingestion_run.status=failed`.
- Upsert через `INSERT ... ON CONFLICT (well_id, ts, tag_id) DO UPDATE`
  (SQLAlchemy Core) — идемпотентность без дублей при повторной загрузке.

Последствия: если позже понадобится, чтобы CSV-рапорт писал сразу в
`daily_production` (минуя допущение "сначала сырьё, потом аллокация") —
это отдельное решение, ingestion сейчас на это не рассчитан.

### 2026-09-16: Валидация замеров АГЗУ (src/calc/validation.py)

Контекст: первый расчётный модуль — набор из 8 независимых правил валидации
well_test, сейчас эта работа делается глазами в Excel.

Решение:
- Разделение на `validation.py` (чистые функции `rule(test, context) ->
  ValidationResult`, без БД — тестируются без сессии) и
  `validation_runner.py` (сборка `RuleContext` из БД, batch-прогон по
  периоду, отчёт `ValidationReport`).
- `is_valid = False`, только если провалилось хотя бы одно `error`-правило
  (`duration_check`, `physical_bounds`, `telemetry_consistency`).
  Остальные 5 — `warning`: используем замер, но помечаем.
  `validation_flags` расширяет формат, который уже писал
  `scripts/synthetic/dirty.py` (`{"errors": [...]}`), добавляя
  `"warnings"` и `"details"` — обратной совместимости не ломает.
- Все пороги — `config/validation_rules.yaml`, резолюция
  default → `overrides.field[<id>]` → `overrides.well[<id>]`.
  Для `duration_check` добавлен `by_node_type` (agzu/dns/gu) поверх этой
  цепочки — в схеме нет отдельного "типа замерной установки", это
  ближайшее осмысленное сопоставление с тем, что реально есть
  (`gathering_node.node_type`).
- `material_balance` — по договорённости с автором, две независимые
  проверки (по жидкости и по нефти) внутри одного правила: `passed`,
  только если обе укладываются в допуск, но `details` показывает
  расхождение по каждому показателю отдельно.
- "Смена режима" (штуцер/уставка частоты ЭЦН) как объясняющее событие
  для `deviation_from_previous`/`water_cut_jump` — сознательно НЕ
  реализована (по решению автора): в схеме нет отдельной таблицы для
  этого, покрываем только ГТМ/сменой насоса/выходом из простоя.
- `staleness` считается от предыдущего ВАЛИДНОГО замера до этого
  (`test.ts_start − previous_valid.ts_end`), не от "текущего момента" —
  работает одинаково и в batch, и в будущем real-time прогоне.
- `telemetry_consistency`: отсутствие телеметрии тока ≠ противоречие,
  правило проходит с пометкой "нечем проверить".

Последствия: если понадобится учитывать смену режима — нужен либо новый
источник данных о нём (например, детекция по скачку `esp_freq_hz` в
телеметрии), либо явная таблица событий смены уставки.

### 2026-09-16: Back-allocation (src/calc/allocation.py)

Контекст: распределение факта добычи узла по скважинам — пропорциональный
метод, K = Qфакт_узла / Σ(Qзамер_i × КЭ_i).

Решение:
- Аллокация ведётся **по 4 фазам независимо** (нефть/жидкость/вода/газ) —
  у каждой свой K, своя проверка границ [0.7, 1.3], свой инвариант суммы.
  Из-за этого `daily_production.allocation_factor` перестал быть одним
  числом — стал `{"oil": K, "liquid": K, "water": K, "gas": K}` (JSONB).
  Добавлены `allocation_method`/`confidence` (миграция `98ac2912cfae`,
  встроена в цепочку до Timescale-специфики, как и предыдущие правки схемы).
- **K вне границ — всё равно применяется**, но помечается предупреждением
  (`k_out_of_bounds:<фаза>`). Это сознательный выбор в пользу инварианта
  "сумма по скважинам = факт узла" — он не нарушается никогда, даже когда
  K выглядит подозрительно. Отказ от применения K сделал бы invariant
  невыполнимым по определению.
- Патологический случай "все КЭ = 0, но факт узла не ноль" (нечего
  пропорционально делить) — K не считается (`None`), всем скважинам 0,
  флаг `no_measured_basis:<фаза>`. Инвариант в этом вырожденном случае не
  держится — альтернативы (кроме отказа от аллокации по этой фазе) в
  задании не было, а придумывать метод распределения без всякой
  измеренной основы значило бы гадать.
- Округление до копеек с коррекцией остатка на крупнейшую скважину узла
  (`_round_with_residual_correction`) — иначе сумма округлённых долей
  расходится с фактом на 1-2 копейки на некоторых наборах чисел.
- Экстраполяция устаревшего замера — простая экспоненциальная по первой и
  последней точке из последних N (по умолчанию 3) валидных замеров, без
  полноценного DCA (Арпса) — по решению автора, до появления отдельного
  модуля DCA.
- Аналог для новой скважины без замеров — медиана свежих валидных замеров
  скважин того же объекта разработки (`completion.reservoir_id`).
- КЭ: приоритет источника часов работы — телеметрия тока ЭЦН → журнал
  простоев → суточный рапорт (`measurement`, тег `hours_on_daily`).
  Отсутствие записей в `downtime` считается достоверным "простоев не
  было" (КЭ=1), а не отсутствием данных — поэтому суточный рапорт как
  источник КЭ реально используется редко (только когда ещё нет ни
  телеметрии, ни самого журнала простоев для скважины).

Последствия: если появится полноценный DCA-модуль — `extrapolate_exponential`
в `src/calc/allocation.py` стоит заменить на вызов настоящей кривой Арпса
по скважине, не переделывая остальной пайплайн.

### 2026-09-16: Потери добычи (src/calc/deferred.py)

Контекст: потери = (потенциал − факт) × время, с разложением по причинам;
три базы потенциала считаются параллельно, но в таблицу идёт одна.

Решение:
- **Разложение недобора нефти** (согласовано с автором): при работающей
  скважине `ΔQн = (Qж_пот − Qж_факт)×(1 − WC_факт) + Qж_пот×(WC_факт − WC_пот)`
  — точная аддитивная variance decomposition Qн = Qж×(1−WC), без остатка.
  Первое слагаемое — `rate_reduction` (реальная упущенная выгода), второе —
  `watering` (естественное истощение, намеренно отдельная категория, не
  смешивается с остальными потерями). Простой считается отдельно, в полной
  ставке Qн_потенциала — во время простоя обводнённость ни при чём.
- **Приоритет базы потенциала** для записи в `deferred_production`:
  `model_forecast` (заглушка, всегда None до шага 9) → `decline_trend` →
  `last_valid_test`. `decline_trend` фитит Арпса (scipy.optimize.curve_fit,
  b∈[0,1.2], Di>0) отдельно на Qн и Qж за 6-12 мес факта; если R² по Qн
  <0.5 — откат на экспоненту (лог-линейная МНК, всегда сходится); если и
  экспонента не построилась (совсем нет положительных точек) —
  `decline_trend` возвращает `None`, и потенциал берётся из
  `last_valid_test`. Обводнённость потенциала для decline_trend выводится
  как `1 − Qн_пот/Qж_пот` из двух независимо подогнанных кривых, не из
  отдельной третьей кривой на WC.
- **"Куст" = `gathering_node`** — отдельной сущности куста в схеме нет
  (решение автора), группировка по кусту и по узлу — одно и то же.
- **Неотработанный фонд** (`well.status IN ('idle','mothballed')`) — не
  проходит через `daily_production`, отдельный проход: весь день потерян
  по последнему валидному замеру, если он не старше
  `idle_fund.max_potential_age_days` (иначе скважина пропускается —
  потенциал слишком ненадёжен, чтобы что-то заявлять).
- Таблица `deferred_production` — новая, миграция `f532bf462c39`
  (создание) + `0b631d9036f7` (hypertable, отдельной миграцией поверх
  `d690f1e15628`, чтобы не трогать уже отработанную). Идемпотентный
  upsert — два частичных уникальных индекса (`reason_id IS NOT NULL` для
  category='downtime', `reason_id IS NULL` для остальных трёх категорий),
  т.к. обычный `UNIQUE` с NULL не гарантирует ровно одну строку на
  (скважина, дата, категория) для не-простойных категорий.

Последствия: batch-прогон на 8 скважинах × 90 суток занимает ~1.5 минуты
в тестах (подгонка Арпса на каждый скважино-день) — это фоновая
периодическая задача, не hot path, но если станет узким местом на полном
промысле — стоит кэшировать подгонку на скважину (она не меняется
внутри одного вызова decline_trend для соседних дат) вместо пересчёта на
каждые сутки заново.

### 2026-09-16: Алерты (src/alerts/) — правиловая детекция, ML не трогаем

Контекст: 8 детекторов аномалий + жизненный цикл (дедуп/каскад/тихие
часы/квитирование) + доставка в Telegram по ролям. ML сознательно не
используется — данных пока мало.

Решение:
- Подписки на алерты (`AlertSubscriber`: chat_id, роль, is_active) —
  новая таблица в БД (решение автора), не YAML — это оперативные данные,
  подписчики приходят/уходят без правки конфига и редеплоя.
- Telegram-бот реализован **по-настоящему** (форматирование, роутинг по
  ролям, кнопки "Квитировать"/"Отложить на 24ч", реальная отправка через
  `python-telegram-bot`), но зависимость опциональная
  (`pip install -e ".[telegram]"`) и активируется только при наличии
  `TELEGRAM_BOT_TOKEN` — решение автора: не платить и не заводить бота
  сейчас, сначала опробовать на своей машине. Без токена
  `send_pending_alerts()` ничего не отправляет и не падает — вся логика
  (форматирование/роутинг/дедуп/каскад) работает и покрыта тестами уже
  сейчас, реальная сеть не нужна.
- `Alert` — `well_id` ИЛИ `node_id` (для группового каскадного алерта
  `node_stopped_cascade`), хотя бы одно обязательно
  (`CHECK well_id IS NOT NULL OR node_id IS NOT NULL`).
- Дедупликация — по активному (`ts_resolved IS NULL`) алерту с тем же
  `(well_id, node_id, type)`: не создаём дубль, обновляем `value`/`message`
  на существующем. Автозакрытие — алерт типа, который детектор проверял
  в этом прогоне, но кандидат для него не пришёл, значит вернулись в
  норму.
- Подавление каскада — только для `well_stopped`: группируем кандидатов
  по узлу, если на одном узле "встало" >= `cascade.min_wells` скважин в
  окне `cascade.window_hours` — один `node_stopped_cascade` вместо N
  отдельных. Остальные детекторы каскад не подавляют (по своей природе
  они не про "все встали одновременно").
- `mtbf_approach` использует `expected_mtbf_days` из конфига (не
  "паспортный" МРП per-насос — такого поля в схеме нет, наработка на
  отказ статистична и не известна заранее per pump).
  **Наблюдение**: на синтетических данных этот детектор срабатывает
  почти на каждой скважине, т.к. генератор (`scripts/synthetic/`) ставит
  `equipment.install_date` на дату бурения (годы до начала истории
  мониторинга), а не "свежий насос на старте истории" — это не баг
  детектора, а особенность уже сданного генератора, чинить не стал
  (не просили, вне рамок этой задачи).
- `production_drop` переиспользует резолюцию потенциала из
  `src/calc/deferred.py` (`potential_from_last_valid_test`/
  `potential_from_decline_trend`) — не дублирует логику подгонки Арпса.

Последствия: если понадобится email/SMS-доставка вместо/вместе с
Telegram — `routes_for()`/`format_alert_message()` уже отделены от
`TelegramSender`, можно добавить параллельный sender без переделки
роутинга.

### API (`src/api/`): FastAPI, JWT, TTL-кэш, чтение поверх существующих расчётных модулей

Контекст: слой доступа делится на три части (API → дашборд → Excel-экспорт),
эта сессия — только API. Требования от автора: 12 эндпоинтов (карточка
скважины, добыча, замеры, телеметрия, события, сводки, потери, алерты,
качество данных), пагинация, pydantic-схемы ответов, OpenAPI (бесплатно от
FastAPI), кэш тяжёлых агрегатов, JWT (сейчас простой, LDAP/SSO — потом).

Решения:
- Пользователи API — **новая таблица `api_user`** (username/password_hash
  bcrypt/role), не переиспользуем `alert_subscriber` (у него нет пароля и
  роль там про рассылку, а не про доступ к API) — так решил автор
  (`"Новая таблица api_user в БД"`). Роли — тот же словарь
  geologist/mechanic/manager, что и у alert_subscriber, плюс `admin`.
- План добычи для сравнения факт/план — **новая таблица `production_plan`**
  (field_id, period_month, planned_oil_t), заполняется вручную — план
  всегда спускается сверху/от министерства, считать моделью нечего
  (`"Новая простая таблица с ручным вводом"`).
- Обе таблицы — в одной миграции `78751628ae84`, сразу после
  `1d7678e78ece` (alerts) и перед hypertable-миграциями — тот же приём,
  что и раньше: `stamp head` → `--autogenerate` → руками переставить
  `down_revision` так, чтобы новая миграция была перед переводом в
  hypertables (эта версия окружения не может проверить TimescaleDB-миграции
  напрямую). Заодно нашлось и исправлено расхождение из прошлой сессии:
  `d690f1e15628` (конвертация исходных 7 таймсерий) и `0b631d9036f7`
  (конвертация deferred_production) оказались двумя параллельными ветками
  от одного родителя (`f532bf462c39`) — `alembic heads` показывал 2 head.
  Выстроены в одну цепочку: `...alerts → api_user/production_plan →
  convert timeseries → convert deferred_production`.
- Пароли — bcrypt через `passlib.CryptContext`. **Важно**: passlib 1.7.4 +
  bcrypt>=4.1 несовместимы (внутренний self-test бросает `ValueError:
  password cannot be longer than 72 bytes` на самом импорте, ещё до
  реального использования) — закреплена версия `bcrypt<4.1`.
- Кэш — свой `TTLCache` (dict + `threading.Lock` + monotonic time) в
  `src/api/cache.py`, без Redis: сервис on-premise, один процесс uvicorn,
  необходимости в распределённом кэше нет.
- `GET /api/deferred` и `POST /api/alerts/{id}/acknowledge` не дублируют
  логику, а вызывают уже существующие `src/calc/deferred_runner.py`
  (`aggregate_losses`/`pareto_by_reason`) и
  `src/alerts/lifecycle.py::acknowledge` — `acknowledged_by` берётся не из
  тела запроса, а из username в JWT.
- `GET /api/wells/{uwi}/events` — единая шкала на клиент: объединяет
  `gtm_event`, `equipment` (спуск/подъём — как "ремонт") и `downtime` по
  одной скважине, сортирует по дате. Отдельной сущности "ремонт" в
  схеме нет — используется история монтажа/демонтажа оборудования.
- `GET /api/wells/{uwi}/production?granularity=` — 'day' отдаёт сырые
  строки `daily_production` как есть (включая `allocation_method`/
  `confidence`); 'week'/'month'/'ytd' — агрегаты (сумма по объёмам,
  среднее по `hours_on`/`ke`), поля метода/уверенности аллокации у
  агрегата не имеют смысла и обнуляются.
- Тесты — `tests/api/`, `TestClient` с переопределённым `get_db` на ту же
  `db_session` (та же откатываемая транзакция, что и у остальных тестов
  проекта) — реальный HTTP-слой поверх настоящей тестовой БД, не моки.

Последствия: дашборд (следующая сессия) может напрямую читать эти
эндпоинты — пагинация и формат ответов уже зафиксированы. CORS сейчас
открыт (`allow_origins=["*"]`) с TODO сузить, когда будет известен адрес
дашборда.

### Помесячная добыча (`monthly_production`): вторая гранулярность данных, отдельная от daily_production

Контекст: автор хочет "агент, который анализирует добычу" — без переусложнения,
главное быстро считать по скважинам. Реальные данные заводятся в первую
очередь **помесячно** (как в классическом рапорте разработки — скважина x
месяц), суточные данные тоже появятся, но позже. Показал реальный
многолетний Excel-отчёт одного месторождения (лист "Добыча": 22к+ строк,
помесячно с 1978 года) — оказалось, что это не просто суточный/месячный
рапорт, а целый годовой отчёт по разработке с планом/фактом по КИН/НИЗ/НГЗ
(геологические запасы) — то, что явно вне нашей системы (см. "не делать":
не заменяем гидродинамическую модель). Из всего отчёта взяли только то,
что действительно можем и должны считать сами — помесячную добычу по
скважине.

Решения:
- **Новая таблица `monthly_production`**, не смешивается с `daily_production`
  — разный смысл строки (месяц vs сутки), разные агрегаты поверх неё.
  Поля близко к реальному отчёту: `calendar_days`/`working_days` (у разных
  компаний дебит считают то от календарных, то от отработанных дней),
  `q_oil_t`/`q_water_t`/`q_liquid_t`/`q_gas_m3`/`gor`/`water_cut_pct`/
  `q_oil_rate_t_d`.
- **Сознательно НЕТ CHECK на физическую правдоподобность** (дебиты >= 0,
  обводнённость 0-100, working_days <= calendar_days) — по аналогии с
  `well_test` (см. ADR выше). Первая версия миграции такие CHECK содержала
  — и тут же упала на реальном файле месторождения (напр. обводнённость
  112% из-за опечатки источника). Исправлено сразу же: как и `well_test`,
  таблица принимает "грязные" значения, задача их отфильтровать —
  будущий слой валидации, а не БД. Единственный оставшийся CHECK —
  `calendar_days BETWEEN 1 AND 31`, это не физическое допущение, а
  математический факт о месяцах, нарушить его нельзя в принципе.
- **Загрузка — конфигурируемый маппинг колонок**
  (`src/ingestion/mappings/monthly_production/*.yaml`), не жёсткий парсер
  под одну компанию: "разные компании собирают по-другому, но логика
  одинаковая" (цитата автора). Скважина резолвится через тот же
  `well_alias`/`resolve_well_id`, что и в остальном ingestion. Объект/
  горизонт по строке резолвится в `reservoir` (по `field_id` + `name` +
  `horizon_code`), если не находится — `reservoir_id` остаётся NULL,
  запись всё равно грузится (координаты объекта не критичны для расчёта
  дебита).
- `q_oil_t`/`q_water_t` **не обязательны** к заполнению в источнике (в
  отличие от `q_liquid_t`/`calendar_days`) — пустая ячейка добычи по фазе
  в реальных рапортах означает "ноль в этом месяце" (скважина работает на
  100% обводнённости), а не "не заполнено". Обнаружено на реальных
  данных: без этого правила 58 легитимных строк "чистая вода" улетали в
  карантин как будто это ошибка.
- Недостающие `q_water_t`/`water_cut_pct`/`q_oil_rate_t_d` довычисляются
  простой арифметикой (вода = жидкость − нефть и т.п.), только когда
  источник их не прислал — то, что прислал источник, в приоритете, поверх
  него не пересчитываем.
- **Расчётный модуль** `src/calc/monthly_analysis.py` (+`_runner.py`) —
  без Арпса и подгонки кривых, максимально просто: последний месяц,
  дельта к предыдущему (абс. и %), накопленная добыча, обводнённость.
  Двухслойный паттерн (чистая логика / БД-обвязка), как и остальные
  `src/calc/*`.
- **Проверено на реальных данных одного действующего месторождения**
  (79 скважин, история с 1978 года, файл предоставлен автором) — не
  синтетика. Сумма загруженной добычи (8 039,5 тыс. т) сошлась с
  накопленной добычей, посчитанной в самом исходном файле (8 169,9 тыс.
  т) с точностью ~1.6% (расхождение — карантин из-за `#DIV/0!` в
  исходных Excel-формулах на нескольких скважина-месяцах). **Сами эти
  реальные данные и загрузочный скрипт-бутстрап в репозиторий не
  коммитятся** — использовались только локально для проверки; тесты в
  `tests/` по-прежнему на синтетических/выдуманных числах.

Последствия: API/дашборд пока НЕ научены читать `monthly_production` —
это следующий шаг, когда понадобится показывать её на карточке скважины
или в фонде. Суточный конвейер (`daily_production`, валидация, аллокация,
потери, алерты) не тронут и ждёт своих суточных данных, когда они появятся.

### API/дашборд научены читать monthly_production

Контекст: предыдущий пункт закончился словами "API/дашборд пока не
научены читать monthly_production" — это тот шаг.

Решения:
- Два новых эндпоинта в существующем `src/api/routers/wells.py` (не
  отдельный роутер — это ресурсы конкретной скважины, как `/production`,
  `/tests`): `GET /api/wells/{uwi}/monthly-production` (сырые строки за
  период) и `GET /api/wells/{uwi}/monthly-summary` (быстрая сводка,
  переиспользует `calc/monthly_analysis_runner.get_well_summary` —
  никакой логики в самом роуте).
- Отдельный роутер `src/api/routers/monthly_production.py` с
  `GET /api/monthly-production/wells` — сводка сразу по многим скважинам
  (для фонда), т.к. это не ресурс одной скважины, а агрегат по фонду.
- Дашборд: карточка скважины — новая полноширинная панель "Помесячная
  добыча" (график Qж/Qн/обводнённость по месяцам) + 4 строки в паспорте
  (дебит/обводнённость/дельта/накопленная добыча за последний месяц).
  Фонд скважин — 3 новые колонки (последний месяц, дебит нефти,
  обводнённость, тренд со стрелкой ▲/▼) поверх уже существующей таблицы,
  плюс попали в CSV-экспорт.
- Проверено визуально в браузере на тех же реальных 79 скважинах
  месторождения (см. предыдущий пункт) — карточка скважины REAL-24
  показывает всю 40-летнюю историю добычи (с 1978), классическую кривую
  падения дебита и рост обводнённости до ~96%, фонд скважин корректно
  считает дебит/обводнённость/тренд по всем 79 скважинам сразу.

### Плотность нефти по горизонту (`reservoir.oil_density_t_m3`)

Контекст: готовим почву под загрузку суточных данных нового формата
(рапорт скважина x сутки с объёмными дебитами — пример от автора,
явно помеченный как "ПРИМЕР/ШАБЛОН"). У части источников дебит нефти
дан только в м3/сут, а не в тоннах — нужна плотность, чтобы перевести.
Плотность — свойство пласта (горизонта), не скважины и не суток, поэтому
не тащим её в каждую строку добычи, а храним одним значением на объект.

Решения:
- Новая колонка `reservoir.oil_density_t_m3` (nullable) — не отдельная
  таблица, плотность это атрибут уже существующего `reservoir`
  (объект/горизонт), не новая сущность.
- `scripts/set_reservoir_density.py` — CLI по образцу
  `create_api_user.py`, чтобы завести/поменять плотность без похода в БД
  руками: `--field --reservoir --density` или `--list` для просмотра.
- `GET /api/reservoirs` + `PATCH /api/reservoirs/{id}` — то же самое
  программно (и в перспективе — с экрана дашборда, если понадобится
  редактировать оттуда).
- Приоритет при загрузке источников (когда дойдёт до суточного
  загрузчика): если источник прислал свою плотность — берём её (как и
  с помесячными данными, источник в приоритете); если нет — берём эту
  справочную по горизонту скважины; если нет ни то ни другое — не
  выдумываем число.

Последствия: суточный загрузчик под новый формат (с объёмными дебитами)
может теперь конвертировать в тонны без плотности в каждой строке файла.
Сам загрузчик — следующий шаг, ещё не сделан.

### Суточный загрузчик добычи (`src/calc/daily_report.py` + `src/ingestion/daily_report_*`)

Контекст: детальную бизнес-логику дал автор (уже готовой спецификацией —
описал сам, не додумывал я). Перед реализацией нашёл два расхождения с
уже сделанным и переспросил, а не стал молча выбирать сам — ответ был
"делай как предложил":

- **Плотность** — спецификация просила отдельный YAML/JSON-конфиг
  `field_id -> {oil_density, water_density}`. Решили не плодить второе
  место хранения плотности — расширили уже существующий `reservoir` (см.
  предыдущую запись): добавили `water_density_t_m3` и флаг
  `density_confirmed` (default `False`), обновили
  `scripts/set_reservoir_density.py` и `PATCH /api/reservoirs/{id}`.
- **`source_type`** (`rate`/`accumulated`) — берётся буквально как в
  спецификации: колонка в каждой строке файла, без попытки завести его
  как статичное свойство скважины в master-data.

Ключевое разделение по ТЗ: **"дебит"** (нормированная на 24ч интенсивность)
vs **"добыча за сутки"** (факт за календарные сутки). Как одно
пересчитывается в другое — зависит от `source_type` у каждой строки:
`rate` (периодический замер, экстраполирован на 24ч) → добыча = дебит ×
(часы/24); `accumulated` (ГЗУ/АГЗУ/Спутник — накопительный счётчик) →
добыча = значение как есть, БЕЗ домножения на часы/24. **Если `source_type`
не указан или неизвестен — добыча сознательно не считается** (все объёмы
`None`), строка уходит в "требует внимания", а не тихо предполагается
дефолтом — ровно то, что просил автор ("не угадывать").

Решения:
- Двухслойный паттерн, как и остальные `src/calc/*`: `daily_report.py` —
  чистая логика (`compute_well_day`, `summarize_field_day`,
  `attention_rows`), без БД; `src/ingestion/daily_report_loader.py` —
  резолюция скважины/объекта/плотности + upsert + карантин.
- Пишем прямо в **уже существующую `daily_production`**, не заводили
  новую таблицу — `allocation_method` ('measured'/'extrapolated') 1:1
  ложится на `source_type` ('accumulated'/'rate'), `confidence`
  ('high'/'low') — на `need_confirmation`. Схема эту развилку уже
  предполагала, хотя раньше туда писала только аллокация от узла.
- **Дебит и газовый фактор (ГФ) не персистятся** — в `daily_production`
  для них нет колонок; остаются только в `WellDayResult` (для детального
  лога/отчёта "требует внимания"), в БД идёт только посчитанная добыча.
- Валидация (все правила из ТЗ реализованы как отдельные проверки, не
  одним блоком): часы работы вне [0,24] — ошибка; отрицательные значения
  — ошибка (не `abs()`); часы=0 при ненулевом дебите — ошибка
  рассогласования данных; часы частичные (0 < ч < 24) без заполненного
  примечания — ошибка, не предупреждение. Любая ошибка валидации — тоже
  блокирует расчёт добычи (не просто помечает), строка идёт в карантин
  (`reason='invalid_value'`) с текстом ошибки.
- `_resolve_density()` — плотность горизонта скважины через
  `Completion.reservoir_id` (тот же путь, что уже использовался в
  `deferred_runner._well_dimension_maps`). Нет `Completion`/`Reservoir`
  или `density_confirmed=False` — не блокирует расчёт (дефолт 0.86/1.0
  всё равно применяется), но пишет `logger.warning` и помечает
  `need_confirmation=True` — ровно то явное предупреждение, которое
  просил автор вместо тихого дефолта.
- **Проверено на реальном файле-примере от автора** ("ПРИМЕР/ШАБЛОН",
  лист "Детализация по скважинам", 15 скважин × 7 суток = 105 строк) —
  в этом файле НЕТ колонки `source_type`, поэтому загрузчик корректно не
  записал ни одной строки в `daily_production` (0 из 105), все 105 ушли
  в "требует внимания" с причиной "не указан source_type" — именно то
  поведение, которое требовало ТЗ. Заодно сверил саму формулу: в файле
  уже была готовая "Дебит нефти, т/сут", посчитанная от объёмного дебита
  через плотность 0.86 — подставил те же числа в `compute_well_day` и
  получил совпадение до 6 знака, формула (п.5 ТЗ) реализована верно.

Последствия: "Утренняя сводка"/"Анализ потерь"/"Качество данных" на
дашборде смогут показывать что-то осмысленное, как только появятся
реальные суточные файлы С колонкой `source_type` — сам загрузчик к этому
готов, дело за подключением к API (следующий шаг, ещё не сделан).

## Не делать

Сознательно **не реализуем** в рамках этой системы:

- **Запись/управление в контур АСУ ТП.** Система строго read-only
  по отношению к промысловым объектам.
- **Замену SCADA** или дублирование её функций реального времени.
  Это аналитический слой поверх, не диспетчерская система.
- **Облачное развёртывание.** Только on-premise, внутри корпоративного контура.
- **Универсальный коннектор "под любой источник данных".** Строим под
  конкретные источники, которые реально появятся, без абстракций "на будущее".
- **Автоматическое принятие решений/управляющих воздействий** на основе
  алертов — система только информирует, решения принимает инженер.
- **Замену гидродинамической модели** расчётами внутри системы. Прогноз
  модели — внешний вход, который сравнивается с фактом, не пересчитывается.

## Правила работы с автором проекта

- Прежде чем писать код по новой задаче — **сначала предложить план и
  дождаться "ок"**.
- Если промысловая логика неясна — **спрашивать, не придумывать формулу
  самостоятельно**.
- **Никакого over-engineering**: не добавлять абстракции "на будущее".
- Каждый расчётный модуль сопровождается **тестами с понятными числовыми
  примерами**.
- Писать **небольшими итерациями**, после каждой — запускать тесты.
